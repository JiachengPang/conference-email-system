## Project Overview
AI-powered conference email management for AAAI/NeurIPS/ICML/ICLR. Two-lane workflow:
- FAQ Lane: high-confidence emails auto-replied using retrieved policy text only
- Human Review Lane: ambiguous/sensitive emails get an AI draft + chair approval

## Ticket Direct-Links & Shareable URLs (Piece B-ticket-lookup)
`/tickets/{ticketId}` is a standalone, shareable page for one ticket — the **same** detail view as the queue, opened directly by Zendesk ticket number (Zendesk-style deep link). It resolves the email via a **dedicated backend lookup**, not a queue-array search, so a ticket URL works even when that row isn't on the current queue page.
- **Backend endpoint** — `GET /api/v1/emails/by-ticket/{ticket_id}` (`emails.py::get_email_by_ticket` → `EmailRepository.get_email_by_zendesk_ticket_id`). `ticket_id` is typed `int`. **Found** → `{email, audit_trail}` (byte-identical shape to `GET /emails/{email_id}`, same `_email_to_dict`/`_audit_to_dict`). **No match** (unknown id, or a row whose `zendesk_ticket_id` IS NULL / non-Zendesk) → **404** `{"detail": "No email found for ticket id {id}"}`. **Non-numeric** path segment → **422** (FastAPI, before the handler). Declared **before** the `/{email_id}` catch-all (two-segment static path — order is load-bearing).
- **Shareable-URL convention** — `${window.location.origin}/tickets/{zendesk_ticket_id}`, built from the browser origin (**never hardcode localhost/a domain**), so links are correct in every environment. The "Copy link" button in `EmailDetail.tsx` uses this. **Use this same `{origin}/tickets/{id}` pattern for any future shareable-link feature.**
- **One shared implementation** — `/queue` and `/tickets/[ticketId]` both render the single `EmailWorkspace` (`frontend/src/components/email/EmailWorkspace.tsx`): filter sidebar, drag-resize, list, detail pane, and all chair actions (approve→send→advance, reroute, reassign, retry) live there. **Change filters/layout/detail once, both routes get it — no duplicate implementations, no drift** (a `shared-workspace-identity` test guards against a fork). Selection is the only per-route difference: `/queue` uses `selectionMode="id"` with a constant `null` (empty "select an email" landing — no auto-redirect; a row click is `router.push('/tickets/{ticketId}')`, not local state); `/tickets/[ticketId]` uses `selectionMode="email"`, fetched via `useEmailByTicket` → `getEmailByTicketId` (client fn in `lib/api/emails.ts`). Its query key `["emailByTicket", ticketId]` is invalidated by every email action, so the detail refreshes immediately (not on the 15s poll).

### 2026-07-26 — Policy EXCLUSION: chairs can remove a citation and re-draft without it — Complete · 9 pieces · committed to `main`
The counterpart to manual invoke: a chair can now remove ANY citation (retriever-found or their own forced pick) and re-draft on what remains. Built as `excluded_policy_ids: list[str] | None` on `RedraftRequest` — **no migration**, persisted in the existing `retrieval_context` JSON. Multi-forced "add several" was deliberately **not** built (drafter-prompt risk); the chair swaps by removing what they don't want and forcing the one they do.
- **Exclusion is a PRE-FILTER, and that is why it carries none of the multi-add prompt risk.** Excluded chunks are dropped from the ranked set before the drafter is called, so they never enter the prompt — there is nothing to instruct the model about. `drafter.py` is **untouched** and no real-LLM re-validation was needed, unlike the forced-policy wording which took two rounds (task 4 → 4d) to stop the model abandoning the requester's question.
- **⚠️ Matching is on LINEAGE ROOT, never the literal `policy_key`** (`resolve_lineage_roots` in `orchestrator.py`, shared with the sweep). `edit_policy` mints a NEW key for an edited policy (`int_foo` → `int_foo__v2`) and retires the old row, so an exact-key exclusion goes stale **on precisely the event that runs the sweep** — a KB edit — and the chunk the chair removed would quietly reappear under its new name. Note the asymmetry with forcing: **forced fails safe** (a retired key resolves to `None`, so it just stops forcing) while **exclusion fails open** (an unmatched key stops excluding). That asymmetry is the whole reason root matching is mandatory here and was optional there. `RetrievedChunk` carries no `root_key`, so roots come from one batched `get_by_keys` → `PolicyRepository._root_of(row)`, with an unknown key mapping to **itself** so a bad id never widens the filter.
- **Precedence: EXCLUSION ALWAYS WINS over forcing.** If a key is both forced and excluded, no forced chunk is appended (`forced_excluded` guard, surfaced on the trace). Without it the ordering silently *undoes* the removal — the key is filtered out of the ranked set, then resolved and appended straight back. That would have been a contradiction resolved by accident of sequencing rather than by rule. Removal is the more recent, more specific intent, and failing toward fewer policies is the safer direction.
- **Minimum-1 guard lives in the ENDPOINT, not the pipeline** — because the re-draft is async (202 + background task), a check after scheduling has no response left to reject with and could only be a silent no-op or a stranded ticket. It compares against the email's stored `retrieval_context.retrieved_ids` (the exact cards the chair is looking at) rather than dry-running retrieval, which would re-issue a distiller model call and, being non-deterministic, could disagree with the run that follows. **409** with a plain-English reason. A still-standing forced policy **rescues** an otherwise-empty set — "remove all three and ground on this one instead" is the swap workflow the feature exists for and must not be rejected. Fails OPEN for a legacy NULL-context row. Best-effort by nature: the redraft re-runs retrieval, so the guard covers the common case, not a hard invariant.
- **Sweep parity**: `_fresh_topk_ids` re-applies exclusions in the SAME order as `_compute` (filter → force, exclusion beating a conflicting forced key) and carries `excluded_policy_ids` into `new_ctx`, so a chair's curation survives someone else's KB edit. Both paths share `resolve_lineage_roots` / `resolve_forced_chunk` so the rules cannot drift — the pattern established in 3e. A normal ticket's context still keeps exactly its five keys (regression-pinned).
- **Reset semantics**: exclusions are per-draft. `reprocess_email_with_thread` (follow-up) calls `_compute` with no extras and never reads prior context, so a follow-up resets to normal retrieval. Only the KB-edit sweep carries them forward, deliberately.
- **Frontend — removal is STAGED, not per-click** (`EmailDetail.tsx`): the X marks a row, and one **"Re-draft without them"** submits the whole set. Per-click would be 3× model spend for two throwaway drafts, and worse: each re-draft is async and `_compute` recomputes from the row's subject/body knowing only *its own* exclusion list, so overlapping clicks would let the last writer silently drop the earlier removals. Removing your own forced pick clears the "Added by you" badge and the success banner (restored on un-stage, since the durable flag is untouched). Confirmed in production: exactly 1 row, isolated not systemic, but fully reproducible on any policy.

- **`retire()` correct as-is, unchanged**: a standalone soft-delete implies no successor, so writing a `superseded_by` would fabricate one. The asymmetry with `edit_policy` is intentional. Fixing the single write in `reactivate` closes the state entirely. Cannot create two editable tips — the reactivate endpoint already 409s if any lineage sibling is `active`.

### 2026-07-28 (later) — Queue pagination: `total` transient-zero window — **TWO** confirmed defects fixed (frontend-only)
One root cause, two independent user-visible bugs. `useEmailQueue` returned `total: data?.total ?? 0`, and with no `placeholderData` React Query has **no data at all for a key it has not fetched yet** — so `total` read **0** for one render on every key change. `EmailWorkspace` derives `pageCount = Math.max(1, Math.ceil(total / QUEUE_PAGE_SIZE))`, which turns a 0 total into **"1 page"**, and the stale-page clamp (`page > pageCount → setPage(pageCount)`) then reset the page. **`Math.max(1, …)` manufacturing a floor of 1 out of "unknown" is the whole bug** — the clamp could not distinguish *"the set shrank to 1 page"* from *"we don't know the count yet"*.
- **Defect 1 (reported): clicking a page number silently bounced back to page 1 on the FIRST click, worked on the second.** Nothing was stale and no closure was involved — the discriminator is purely **whether that page's query key has cached data**. First click → uncached → `total` 0 → clamp → page 1; the in-flight fetch still completes and populates the cache, so the second click reads the cached `total` synchronously and sticks. Correlated with "pages just exposed by truncation" only because those are exactly the pages never visited. Reproduced identically via the **Next chevron**.
- **Defect 2 (NOT reported, found during verification — a separate PRE-EXISTING bug, not a side-effect of fixing defect 1): the persisted queue page was silently discarded on every hard reload.** On a cold cache there is no previous data for `placeholderData` to keep, so `total` is 0 on the first render and the clamp reset the page before the count ever arrived. Proven empirically, not argued: with `confmail.queuePage=5` the workspace requested offsets **`[400, 0]`** and landed on page 1. It only ever worked inside an SPA session because the cache was warm. **This is fixed by the same `hasCount` guard and deserves its own line — it predates this session's work and was never part of the original report.**
- **Fix 1 — at the source** (`useEmailQueue.ts`): `placeholderData: keepPreviousData` (**v5 API**: import the `keepPreviousData` helper; v4's boolean `keepPreviousData: true` is REMOVED in v5 — verified against installed **5.101.1**, not inferred from the semver range). Fixing the hook rather than only the clamp keeps `total` honest for every consumer (count text, empty states). No conflict with the `staleTime: 30_000` / `retry: 1` defaults — both are orthogonal to "what is returned for a key with no data". Blast radius is one caller: dashboard (`["emailQueue"]`) and auto-replies (fixed `{lane:"faq"}`) never change key. `isFetching` deliberately NOT exposed — grep confirmed zero consumers.
- **Fix 2 — the clamp keeps its job, gated** (`EmailWorkspace.tsx`): `const hasCount = total > 0;` … `if (hasCount && page > pageCount)`. **Gated on `total > 0`, NOT on `!isLoading`** — with placeholder data present v5 reports `status:"success"`, so `isLoading` is false mid-transition AND false in the error state; it no longer identifies "count unknown". `total > 0` states the actual precondition. A genuinely empty set skips the clamp harmlessly (`Pagination` renders nothing at `pageCount <= 1`). The clamp was **kept, not deleted** — it still has a real job (the set shrinking under you on the 15s poll would otherwise strand the user on an empty page).
- **`placeholderData` does NOT cover the error window** — it applies while the query is `pending`; on `error` v5 sets `data: undefined`, so `?? 0` returns. Confirmed empirically (offsets `[0,100,0]` after a rejected page-2 fetch). The `hasCount` guard is what closes it, so a failed fetch now shows the error **without** also yanking the chair back to page 1.
- **Deliberate approved UX change**: with placeholder data the list shows the PREVIOUS page's rows for ~200ms instead of a loading state (standard keep-previous pagination — no layout collapse between pages).
- **Tests +10, both fixes mutation-verified INDEPENDENTLY** (disjoint failure sets prove neither is load-bearing for the other): dropping `placeholderData` fails 3 (hook transient · page-number click · Next chevron); dropping the `hasCount` guard fails 3 (cold mount · failed fetch · **and the genuine-shrink test — without the guard the true clamp lands on page 1 instead of the correct last page 2**). New `useEmailQueue.transient.test.tsx` (3) + `queue-pagination-clamp.test.tsx` (7) mock **only the network layer** so `total`'s pending/success/error transitions come from React Query itself.
- ⚠️ **Why the original bug slipped through, and the standing trap**: all 4 existing pagination test files `vi.mock` `useEmailQueue` to return a **constant `total` regardless of params**, so the transient window cannot exist in them. Deliberately NOT rewritten — a mock faithful to the pre-fix hook breaks those tests, and one faithful to the post-fix hook *is* `keepPreviousData` and so can never catch its own regression. Instead `queue-pagination-behavior.test.tsx` + `queue-pagination-fetch.test.tsx` gained **SCOPE LIMIT headers** naming the blind spot and pointing at the real-hook file. **Anything timing-dependent (loading windows, the clamp, cold mounts, fetch errors) belongs in `queue-pagination-clamp.test.tsx`, never in a hook-mocked file.**

- **UNDECIDED (not a blocker) — long unbroken tokens don't wrap in policy previews.** Measured on the live corpus: **24 tokens exceed 60 chars, longest 108** (Google Forms + AAAI PDF URLs, e.g. `int_reciprocal-reviewer-changes`). Word-breaking is **orthogonal to `white-space`**, so the 2026-07-29 `pre-wrap` newline fix neither caused nor worsened this — it is pre-existing and unchanged. The three clamped previews (`PolicyList` body, `AddPolicyPanel` similar-preview, `PolicySelectPopover` search result) are `overflow: hidden`, so a long URL is **clipped, never escaping its container** — cosmetic, not a layout break. If addressed, it is a `wordBreak: "break-word"` addition **decided as one unit across all three sites** (the `PolicySelectPopover`/`PolicyDetailModal` **detail** views already have it, because they render full text in a scrollable box where clipping hides content a chair must read before approving). Deliberately kept out of the newline workstream to avoid mixing an unrelated layout change into it.
- **UNDECIDED (not a blocker) — `button.tsx`'s primary variant is 4.47:1, marginally under AA.** Its `default` variant ships `bg-[var(--accent)] text-white`, and white on `--accent` (#6366f1) measures **4.47:1 in BOTH themes** (the accent tokens are the same hex in dark and light) against the 4.5:1 floor for body text. Deliberately NOT fixed when found, because it is an app-wide call affecting every primary button, not something to change from inside one component. The one-line fix is `--accent-hover` (#4f46e5, **6.29:1**). `calendar.tsx` already uses `--accent-hover` for its own selected-day / range-endpoint fills — an intentional divergence from the button, documented in its header, so a selected date is not the same indigo as a primary button until this is decided.
- **UNDECIDED (not a blocker) — `#NNNNN` matches Zendesk ticket numbers as well as submission numbers.** The bare `#` is its own cue in `_SUBMISSION_CUE_RE`'s sibling `_HASH_NUMBER_RE`, which is what correctly catches *"submission #10824"* (13.1% of threads) — and also wrongly catches *"your previous request #15345"* / *"Following up on ticket #16106"*. Measured within the multi-number threads: **22% (48/218) include at least one ticket-worded number**, and **7.3% (16/218) include a number equal to the thread's OWN `ticket_id`** — an unambiguous tell an eventual fix could key on. Unaffected by the 2026-08-07 list-widening (which changed how many matches are collected, not what counts as one); if anything the widening makes it slightly more visible, since a false positive now appears alongside the real number rather than possibly losing to it. Tuning the `#` cue trades recall on a real 13.1% pattern against this precision loss, so it needs a deliberate call rather than a quiet regex tweak.
